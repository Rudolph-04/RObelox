# Input timing, hit judgement and networking for a Roblox rhythm game (Laskar Kendang)

Evidence labels used below:
- **[Doc]**: official Roblox Creator Docs or release notes.
- **[Staff]**: a reply from a Roblox engineer on the DevForum.
- **[Measured]**: someone reported a measurement (method noted where known).
- **[Anecdotal]**: a forum opinion or report with no data.
- **[Inference]**: my own reasoning, listed only under "Inferences".

Dates matter because Roblox changes engine behaviour often. Anything before 2024 is flagged as possibly out of date.

Game context used for the inferences: 120 BPM (500 ms per beat). PERFECT ≤ 70 ms, GOOD ≤ 150 ms. Hits are judged on the client against a beat clock built on `workspace:GetServerTimeNow()`. A calibration offset (-200..+300 ms) is applied. After 4 hits the client sends a RemoteEvent with (command id, beat index, quality), and the server checks beat index −2..+1 and command spacing. The game is PvE co-op.

## 1. How precisely can Roblox timestamp player input (InputBegan delay, frame quantization, timestamps, FPS cap)?

### Takeaway
Roblox gives no sub-frame input timestamp. `InputObject` has no time property, and an open feature request confirms that input timing is only known to frame resolution. The best you can do is read `os.clock()` (sub-microsecond precision) inside the handler. That reading is quantized to when the engine processes input that frame: up to about 16.7 ms late at the default 60 FPS cap, and about 4.2 ms at the 240 FPS maximum. OS, driver and device latency come on top of that and can't be seen from Lua.

### Cited Findings
- [Doc] `InputObject` exposes only 5 properties: `Delta`, `KeyCode`, `Position`, `UserInputState`, `UserInputType`, plus `IsModifierKeyDown()`. It has no time-of-input or timestamp property. — [Roblox Docs: InputObject](https://create.roblox.com/docs/reference/engine/classes/InputObject)
- [Doc] `UserInputService.InputBegan` "fires when a user begins interacting with an input device such as a mouse or gamepad" and "only fires when the Roblox client window is in focus". The docs say nothing about frame timing or latency. `gameProcessedEvent` "Indicates whether the engine internally observed this input and acted on it… Generally this refers to UI processing, so if a button was touched or clicked from this input…" — [creator-docs UserInputService.yaml](https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/reference/engine/classes/UserInputService.yaml)
- [Anecdotal, feature request, 2023] A DevForum feature request asking for `InputObject.TimeSinceInputUpdate`/`TimeOfInput` states: "there is currently no way to know when a mouse, keyboard, or other input was made at a resolution finer than the player's framerate". It says sub-frame inputs are "aggregated onto the previous frame", and that scripts "must assume either that the input was made at the time of the previous frame, or the next frame". A later commenter building a tick-rate-less shooter says they are "unable to … determine accurate sub-frame timestamps for player inputs". I found no evidence this has shipped: the current InputObject docs still list no time property. — [DevForum: "InputObject.TimeSinceInputUpdate" property request](https://devforum.roblox.com/t/inputobjecttimesinceinputupdate-property-to-support-beyond-tick-rate-input-processing/2226487)
- [Doc] `os.clock()` "Returns elapsed time in seconds since an arbitrary baseline with sub-microsecond precision". It is "useful for comparing durations between two events that occur on the same computer" and is "the best option for benchmarking". `os.time()` "should be avoided in new work". — [creator-docs os.yaml](https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/reference/engine/libraries/os.yaml)
- [Doc] The task scheduler handles "detecting player input" as part of each frame, and runs PreAnimation, PreSimulation, PostSimulation/Heartbeat and PreRender in a fixed order. The exact position of the input stage appears only in a diagram. — [Roblox Docs: Task scheduler](https://create.roblox.com/docs/studio/microprofiler/task-scheduler). A 2023 DevForum reporter reads the documented order as "input → rendering → physics → Heartbeat". — [DevForum (2023)](https://devforum.roblox.com/t/heartbeat-executes-in-between-input-callbacks-and-renderstepped-on-mobile/2220582)
- [Staff, 2023] On mobile, Roblox added a second input-processing pass. Touch input moved earlier in the frame, before physics/Heartbeat. Staff (evisceratedpumpkin): "It improves input latency and frame rate." Staff (prpht) said it would "gradually [roll] out to all platforms" and "I personally wouldn't call relying on the stages order a perfect practice." Do not rely on the order of input callbacks relative to RenderStepped/Heartbeat. — [DevForum: Heartbeat executes in between input callbacks and RenderStepped on mobile (Mar 2023)](https://devforum.roblox.com/t/heartbeat-executes-in-between-input-callbacks-and-renderstepped-on-mobile/2220582)
- [Anecdotal/announcement] The Roblox client has a "Maximum Frame Rate" setting. At launch it offered Default (= 60 FPS), 60, 120, 144 and 240. 240 is the ceiling. A forum explanation says going higher would require detaching physics from the frame loop. One commenter asked when the setting would come to Mac, so Mac availability was unclear at that point. — [DevForum: Introducing the Maximum Framerate setting](https://devforum.roblox.com/t/introducing-the-maximum-framerate-setting/2995965); [Dexerto how-to](https://www.dexerto.com/roblox/how-to-change-your-fps-in-roblox-2751173/). A third-party guide claims later values (160/165/180/200) were added. Unverified. — [hone.gg](https://hone.gg/blog/what-is-fps-unlocker-for-roblox/)
- [Anecdotal bug report] Some reports say the engine stays at 240 FPS regardless of the `FramerateCap` in GlobalBasicSettings_13.xml, or that changing the cap did not apply. — [DevForum: Roblox caps fps at 240 regardless of …](https://devforum.roblox.com/t/roblox-caps-fps-at-240-regardless-of-globalbasicsettings13xml-framerate-cap/4451048)
- [Measured, informal, Roblox-specific] A MIDI virtual-piano developer measured about 4 frames (≈67 ms) between a key being logged by an external Python process and the key appearing in Roblox. They also measured ≈286 ms between the piano's sound and the game's sound. A commenter suggested Windows input buffering or Roblox input processing as causes. — [DevForum: MIDI based Virtual Piano Engine](https://devforum.roblox.com/t/midi-based-virtual-piano-engine/4745365)
- [Anecdotal, OLD 2019–2020] In a long "Significant input delay" thread, one developer estimated that Roblox has "a major (30-70ms) input latency" even after optimization. The thread reported random spikes up to 300–400 ms tied to high mouse polling rates and borderless-fullscreen (F11) vs true fullscreen (Alt+Enter). A later reply credits Release 447 with a large reduction. Treat as outdated. — [DevForum: Significant input delay (Camera Lag)](https://devforum.roblox.com/t/significant-input-delay-camera-lag/344960)
- [Anecdotal, recent] Users report that input lag appears in some experiences and not others. One says turning off Windows' "optimizations for windowed games" for Roblox helped. — [DevForum: [Input Lag] game was not properly handling my gameplay inputs](https://devforum.roblox.com/t/input-lag-game-was-not-properly-handing-my-gameplay-inputs-resulting-in-laggy-gameplay-in-some-games/3591446). Heavy Lua work on the same frame (raycasts, spawning) is cited as a cause of delayed input handling. — [DevForum: How to Reduce Input Lag?](https://devforum.roblox.com/t/how-to-reduce-input-lag/2985062)

### Inferences
- [Inference] The quantization error from reading `os.clock()` in the handler is one-sided (always late). It is roughly uniform from 0 to one frame: 60 FPS → 0–16.7 ms (mean ≈ 8.3 ms); 120 → 0–8.3 ms; 144 → 0–6.9 ms; 240 → 0–4.2 ms. The mean part is a constant bias that a calibration offset absorbs. The spread (±8 ms at 60 FPS) is small next to Laskar's ±70 ms PERFECT window, so frame quantization is not a fairness problem at these windows. It would matter at osu!-mania-style ±16 ms windows.
- [Inference] Capture the timestamp as the first statement in the InputBegan / GuiButton.InputBegan handler (`local t = os.clock()`) before any other work. Several drums pressed in the same frame will get nearly identical times. That's fine, since they are physically simultaneous to within a frame.
- [Inference] Players on a 60 FPS cap get a systematically later average judgement than players at 144–240 FPS (≈ 8 ms vs ≈ 2–3 ms of bias). A per-player calibration offset already corrects for this, but the default offset will be slightly off for high-FPS players.
- [Inference] `os.clock()` is the right local clock to stamp inputs: it is monotonic, sub-µs and unaffected by wall-clock changes. Convert it to "beat time" with a separately maintained offset (see section 3) rather than calling `GetServerTimeNow()` inside each handler.

### Gaps
- No official Roblox figure for end-to-end input latency (key → `InputBegan`) on any platform. No current (2025–2026) Roblox-specific measurement found.
- Not found: whether higher FPS also reduces OS→engine input latency beyond the frame-quantization term, or whether input is sampled once per frame on every platform.
- A DevForum thread claims the `Player` object has an input-latency property restricted to CoreScripts — [DevForum (unverified)](https://devforum.roblox.com/t/feedback-on-playerinputlatency/4729864). Not confirmed in the docs.

## 2. Device latency differences: mobile touch (iOS vs Android), GuiButton vs UserInputService, gamepad

### Takeaway
No Roblox-specific per-device numbers exist. General measurements (mostly old) show touchscreens add a lot of latency: ~55–85 ms on 2013-era iPhones and ~110–120 ms on 2013-era Android phones from tap to screen response. Android also usually has larger and more variable audio latency. Wired or 2.4 GHz gamepads add only a few ms. Bluetooth controllers add tens of ms in some tests, but the data is weak and contradictory. Since 2023, Roblox has given touch its own earlier input pass to cut latency.

### Cited Findings
- [Measured, OLD 2013] Agawi TouchMarks (minimal test app, tap → screen response): iPhone 5 = 55 ms average, iPhone 4 = 85 ms, Samsung Galaxy S4 = 114 ms. Android devices clustered at 110–120 ms. — [GamesBeat](https://gamesbeat.com/apples-iphone-5-touchscreen-is-2-5-times-faster-than-android-devices/); [iMore](https://www.imore.com/iphone-5-touchscreen-latency-measured-found-be-25-times-faster-closest-android-device)
- [Measured, OLD 2013] A 240 fps camera test (touch → something displayed) measured iPhone 5 = 81 ms and Nintendo 3DS = 23 ms. The Galaxy S3 had the highest latency among popular phones. The author noted that finger input is hard to measure and seems to add latency. This conflicts with Agawi's 55 ms for the same phone because the methods differ. — [Michael Tsai blog, "Touchscreen Latency" (2013)](https://mjtsai.com/blog/2013/09/23/touchscreen-latency)
- [Measured, academic] An Aalto University thesis on Android tap-feedback latency found about a five-fold difference between devices, measured with a Teensy/Arduino rig. — [Kousa, Aalto thesis (PDF)](https://core.ac.uk/download/145239672.pdf)
- [Measured, other engine] In Unity, the engine's touch API adds "1-2 frames latency" over what the OS reports. Receiving OS touch callbacks directly ("Native Touch", with a hardware timestamp) saved 10–16 ms on a Nexus 5, a maximum of about 16.7–33.3 ms. This shows engine-layer overhead on mobile is about 1–2 frames. It is not a Roblox measurement. — [Unity Discussions: Native Touch (5argon/Exceed7)](https://discussions.unity.com/t/native-touch-faster-touch-via-callbacks-from-the-os-with-a-real-hardware-timestamp/698323)
- [Measured, other engine] A Unity engineer said Android touch input was contending with the Java UI thread, which lowered FPS and raised latency. This was fixed in Unity 2019.4.32f1/2020.3.20f1/2021.2.0b14. It shows Android touch latency depends on implementation details. — [Unity Discussions: Android Latency Problem](https://discussions.unity.com/t/android-latency-problem/860464)
- [Anecdotal, 2026] A small developer's devlog reports median tap-to-motion falling from 124 ms to 91 ms after tuning, tested on an iPhone 13, a Pixel 7 and Windows touch, with no per-platform split. — [Zappers devlog (Apr 2026)](https://zappers-games.pages.dev/devlog-touch-input-latency.html)
- [Staff, 2023] Roblox moved touch input to its own earlier input pass on iOS/Android to "improve input latency and frame rate", with a planned rollout to all platforms. The DevForum reporter noted Studio's emulator cannot reproduce mobile frame-order differences, so test on real phones. — [DevForum (Mar 2023)](https://devforum.roblox.com/t/heartbeat-executes-in-between-input-callbacks-and-renderstepped-on-mobile/2220582)
- [Anecdotal bug, mobile] After a screen-orientation change, new touch InputObjects can stay frozen in `Begin` and never reach `End`. Some of those taps still fired `InputBegan`. — [DevForum bug report](https://devforum.roblox.com/t/after-screen-orientation-change-on-mobile-new-input-objects-sometimes-have-userinputstate-frozen-in-begin-state/3358496)
- [Doc] When a GUI button consumes a touch or click, `UserInputService.InputBegan` still fires, with `gameProcessedEvent = true`. — [creator-docs UserInputService.yaml](https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/reference/engine/classes/UserInputService.yaml)
- [Measured, weak sources, conflicting] Gamepads: Xbox controller wired vs 2.4 GHz dongle differed by about 0.9 ms in one comparison. DualSense numbers vary widely: USB 4.5–7.5 ms vs Bluetooth 18.3–34.6 ms in two tables, but one Windows test (The Nerd Stash) found DualSense Bluetooth 0.98 ms vs Xbox 6.90 ms. Gamepadla lists DualSense BT 9 ms vs Xbox 12.2 ms and says its comparison module "may contain errors". Many of these pages are low-quality SEO pages. — [Gamepadla DualSense vs Xbox](https://gamepadla.com/versus/sony-dualsense_vs_xbox-core-controller.html); [The Nerd Stash](https://thenerdstash.com/which-controller-has-the-lowest-input-lag-in-call-of-duty-warzone-and-black-ops-6); [Alibaba "product insights" (low quality)](https://www.alibaba.com/product-insights/wired-controller-vs-wireless-for-pc-gaming-input-lag-tested.html)
- [Expert devlog] Audio latency is "usually … the largest of the three latencies" (audio, visual, input), and Android is especially prone to it. Wireless controller transmission and frame-based input handling are named sources of input latency. "50-100ms of lag" is common even in competitive fighting games. — [Rhythm Quest Devlog 10: Latency Calibration (Aug 2021)](https://rhythmquestgame.com/devlog/10.html)
- [Anecdotal] In latency-optimized console games like Guitar Hero, "the lowest latency you can hope for is around 60ms with a good TV". — [Michael Tsai blog (2013)](https://mjtsai.com/blog/2013/09/23/touchscreen-latency)

### Inferences
- [Inference] Mobile players will on average register hits noticeably later (tens of ms) than keyboard players. Android will be later and more variable than iOS, especially once audio output latency is included. A single global default offset will be wrong for one group, so use a per-platform default and keep per-player calibration.
- [Inference] For on-screen drum pads, `GuiButton.InputBegan` and `UserInputService.InputBegan` both run in the same input processing for that frame. No source shows a latency difference between them. Use one path per pad to avoid double-counting: check `gameProcessedEvent`, or handle pads only via the GuiButton. Stamp `os.clock()` first thing in whichever handler you use.
- [Inference] Prefer `InputBegan` over `Activated`/`MouseButton1Click` for drums. Click-style events fire on release, which adds the whole press duration to the timing (typically tens of ms for a tap).
- [Inference] Handle the "stuck in Begin" orientation bug: treat each `InputBegan` as a hit and never wait for `End` before judging.

### Gaps
- No measurement of Roblox's touch → `InputBegan` latency on iOS vs Android, or of `GuiButton` vs `UserInputService` event latency.
- No reliable, current (2024–2026) cross-device touch latency benchmark. The best data is from 2013.
- No Roblox-specific gamepad latency figures. The general gamepad data is low quality and conflicting.

## 3. `workspace:GetServerTimeNow()`: accuracy, behaviour, and suitability as a rhythm clock

### Takeaway
Officially, `GetServerTimeNow()` is "the client's best approximation of the current time on the server". It is monotonic, never jumps backwards, and slews to correct itself: it runs at up to 0.6% faster or slower than the local clock. Accuracy is not guaranteed. Community reports say clients agree to within "a few ms". It is fine as a shared beat clock for co-op. Watch for two problems: the 0.6% slewing during a song, and a confirmed October 2026 bug where it returned 0 on some clients for a whole session.

### Cited Findings
- [Doc] "This method returns the client's best approximation of the current time on the server." It returns Unix time in seconds. "It is monotonic; its value will never decrease." It "moves at the same rate as the local clock to within 0.6%." It is "useful for making sure an event starts at the right real-world time" and for periodic corrections that keep a series of events in sync. It errors if called on a client not connected to a server. It is "not suitable for things like timed rewards" because client-side timing can be tampered with. Use `os.clock()` for high-precision benchmarking. — [creator-docs Workspace.yaml](https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/reference/engine/classes/Workspace.yaml)
- [Doc] Introduced in Release 488 (2021) as a "monotonic server time API". — [Release notes 488](https://create.roblox.com/docs/release-notes/release-notes-488)
- [Anecdotal but detailed, possibly engine-informed, May 2023] It is "like `tick()`" (same internal monotonic clock) "with constant synchronization and smoothing on top". It "will slightly slow or speed up time to maintain synchronization" rather than jumping. It applies NTP-like approximate latency compensation, roughly `lastReceivedServerTime + ping/2`. Clients have no accuracy guarantee. The poster (ContextLost) was "a little disappointed" the compensation was added. Another user (May 2025) asked for a non-extrapolated version because the extrapolation causes jitter in physics interpolation. — [DevForum: GetServerTimeNow documentation incorrect…](https://devforum.roblox.com/t/workspacegetservertimenow-documentation-incorrect-and-datetimenow-needs-more-information/1909687)
- [Anecdotal, Sep 2025] "Should be pretty accurate down to a few milliseconds" (averlst). "Used it hundreds of times… a few milliseconds" variation across clients (Frazer). Another user warned that ping differences (70 ms vs 20 ms) could produce larger spreads, but had not used it. No staff replies and no data. — [DevForum: About how accurate is GetServerTimeNow? (Sep 2025)](https://devforum.roblox.com/t/about-how-accurate-is-getservertimenow/3926695)
- [Anecdotal, 2025] It does not appear to make a live request per call: 100K calls showed no rise in network receive. The sync mechanism is undocumented. — [DevForum: How does GetServerTimeNow work? (Jun 2025)](https://devforum.roblox.com/t/how-does-workspacegetservertimenow-work-does-it-replicate-time-on-every-call-or-in-the-background/3673444)
- [Staff, Oct 2026, RECENT BUG] On some live clients, `GetServerTimeNow()` returned 0 for the entire session. This broke countdowns and cooldowns, with reports starting September 30, 2026, mainly on PC and Mac desktop. Staff (PlumJar): "Our telemetry shows this issue impacts a very small set of users". A desktop patch shipped on Oct 16, and "We finished rolling a fix out over this past weekend" on Oct 27. The thread does not confirm a mobile fix. Workarounds: rejoin (sometimes works), shut down the server, or have a community-built RemoteFunction clock sync with local elapsed time. — [DevForum: GetServerTimeNow() returns 0 on client for entire session in live servers (Oct 2026)](https://devforum.roblox.com/t/workspacegetservertimenow-returns-0-on-client-for-entire-session-in-live-servers/4909426)
- [Anecdotal] In Studio, two sessions differed by about a minute because of mismatched system clocks. Live servers reportedly show only ms-level differences. — [DevForum: GetServerTimeNow doesn't return same time between 2 servers](https://devforum.roblox.com/t/getservertimenow-doesnt-return-same-time-between-2-servers/3920554)
- [Doc] `os.clock()` has sub-µs precision, an arbitrary baseline, and is not affected by clock adjustments. `DistributedGameTime` is "not 'Distributed' across the client and the server". On the client it measures time since connecting, and developers shouldn't rely on it. — [creator-docs os.yaml](https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/reference/engine/libraries/os.yaml); [creator-docs Workspace.yaml](https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/reference/engine/classes/Workspace.yaml)
- [Anecdotal, conflicting] Whether `tick()` is monotonic is disputed: one user says no (2022), another says it is monotonic after a startup offset but may drift (2023). One user (2024) reports problems with `tick()` for about 1% of users with bad system clocks. — [DevForum thread 1909687](https://devforum.roblox.com/t/workspacegetservertimenow-documentation-incorrect-and-datetimenow-needs-more-information/1909687)

### Inferences
- [Inference] The 0.6% rate tolerance matters at rhythm-game scale. While the clock is slewing, it can gain or lose up to 3 ms per 500 ms beat, ≈12 ms over a 4-beat command and ≈60 ms over 10 s, relative to `os.clock()` and to a locally playing `Sound`. If music plays on the local audio clock and judgement uses `GetServerTimeNow()`, the two can drift apart by tens of ms during corrections, for example after a ping change.
- [Inference] A robust pattern: (a) keep a local beat clock `beatTime = os.clock() + offset`. (b) Recompute `offset = GetServerTimeNow() − os.clock()` every frame, but only apply corrections smoothly and in small steps, or only between commands or bars, so the clock never jumps mid-sequence. (c) Stamp inputs with `os.clock()`, then convert. This keeps sub-µs precision for inputs while using server time only to anchor the song start.
- [Inference] Guard against the Oct 2026 bug: if `GetServerTimeNow()` returns 0 or a value far from expected (say, more than 10 s away from a server-sent reference), fall back to a RemoteFunction ping-pong sync (server `os.clock()` or `GetServerTimeNow()` + RTT/2) and run on `os.clock()` locally.
- [Inference] For co-op PvE, absolute cross-client accuracy of a few ms (anecdotal) is more than enough. What matters is that each client's clock agrees with what that player hears. Any constant error between them is absorbed by the player's calibration offset.

### Gaps
- No official accuracy figure (ms) for `GetServerTimeNow()` on clients. No published measurement of its jitter or of how often and how strongly it slews.
- Not found: whether the client sync rate or smoothing constants changed after the Oct 2026 fix, or whether the 0-return bug affected mobile.

## 4. Hit windows used by successful rhythm games; how Roblox rhythm games choose them; mobile widening

### Takeaway
Competitive PC rhythm games use tight windows: osu!mania MAX ±16 ms, osu!taiko GREAT ±20–50 ms, Etterna "Marvelous" ≈ ±22 ms. Their outer windows reach ±100–150 ms. Laskar's PERFECT ±70 / GOOD ±150 is more lenient than even the loosest osu!taiko setting, which suits a casual, mobile-heavy, 120 BPM, Patapon-like game. No published Roblox rhythm-game (Funky Friday, RoBeats) window values were found. Taiko (Switch) and Patapon offer difficulty or accessibility options that widen windows, which is a precedent for a "wider timing" option rather than silently widening on mobile.

### Cited Findings
- [Doc, osu! wiki] osu!taiko windows (± ms from note, by Overall Difficulty OD 0–10): GREAT = `50 − 3·OD`. OK = `120 − 8·OD` (OD ≤ 5) / `110 − 6·OD` (OD ≥ 5). MISS = `135 − 8·OD` (OD ≤ 5) / `120 − 5·OD` (OD ≥ 5). — [osu! wiki: Overall difficulty](https://osu.ppy.sh/wiki/en/Beatmap/Overall_difficulty)
  - Computed: OD 0 → GREAT ±50, OK ±120, MISS ±135. OD 5 → ±35 / ±80 / ±95. OD 10 → ±20 / ±50 / ±70.
- [Doc, osu! wiki] osu!mania: MAX ±16; 300 = `64 − 3·OD`; 200 = `97 − 3·OD`; 100 = `127 − 3·OD`; 50 = `151 − 3·OD`. OD 5 gives 49 / 82 / 112 / 136. osu!standard: 300 = `80 − 6·OD`, 100 = `140 − 8·OD`, 50 = `200 − 10·OD`. OD 5 gives 50 / 100 / 150. Stable osu!/taiko windows are up to 0.5 ms narrower per side; a hit counts if `error < round(window)`. — [osu! wiki: Overall difficulty](https://osu.ppy.sh/wiki/en/Beatmap/Overall_difficulty)
- [Anecdotal/partial] Etterna: Judge 4 is described as a 180 ms window, and J7 is half of J4. A user says J4 "Marvelous" is 0–22 ms. StepMania 3.9's Marvelous window is 0.0225 s (≈22.5 ms). The default judge (J4 vs J5) differs between doc versions. — [Etterna 0.71.2 release post](https://forums.etternaonline.com/t/etterna-0-71-2-released/3552); [docs.rs etterna crate](https://docs.rs/etterna); [FFR forum: SM5 timing windows](https://www.flashflashrevolution.com/vbz/node/100084)
- [Anecdotal, community FAQ] Taiko no Tatsujin (Switch) "Easier Hit Timing" "effectively TRIPLES the window to hit a Good, and increases the Ok window by about 25%". No ms values were found. — [r/taikonotatsujin FAQ (mirror)](https://lr.sudovanilla.org/r/taikonotatsujin/comments/mvz94m/frequently_asked_questions_edition_v4)
- [Anecdotal] Patapon grades each drum hit Good / Great / Perfect, and only Great or Perfect sustains Fever. Timing leniency in Patapon 2 depends on the difficulty setting, and Patapon 3 is looser than Patapon 1 by default. No frame or ms values were found. — [Patapon Wiki: Patapon Drums](https://patapon.fandom.com/wiki/Patapon_Drums); [GameRevolution Patapon FAQ](https://www.gamerevolution.com/?p=40216)
- [Anecdotal] RoBeats reportedly lets players upgrade "timing windows" as a stat, so windows are not fixed per player. No ms values were found. — [TV Tropes: Robeats](https://www.tvtropes.org/pmwiki/pmwiki.php/VideoGame/Robeats)

### Inferences
- [Inference] Laskar's PERFECT ±70 ms equals osu!standard's 300 window at OD ≈ 1.7. GOOD ±150 ms equals osu!standard's 50 window at OD 5, and is wider than osu!taiko's MISS window at any OD. This is very lenient, and that is reasonable for a casual game played on phones where touch and audio latency vary by 50–100 ms between devices.
- [Inference] At 120 BPM (500 ms per beat), GOOD ±150 leaves a 200 ms "dead zone" between beats (150–350 ms after a beat). An off-beat press is then clearly a miss and is not snapped to the wrong beat. Don't widen GOOD beyond ±200 ms, or the windows of adjacent beats start to touch.
- [Inference] Rather than silently widening windows on mobile, which breaks fairness on shared co-op leaderboards, give mobile a better default calibration offset. Optionally add an explicit "Easier timing" toggle like Taiko or Patapon, and flag its scores separately if they ever feed rankings.
- [Inference] Frame quantization (≤ 16.7 ms at 60 FPS) plus `GetServerTimeNow` slew (a few ms) together use up only a small fraction of a ±70 ms window. Laskar's windows are safely above Roblox's timing noise floor. Windows tighter than ±30 ms would not be.

### Gaps
- No published ms windows for Roblox rhythm games (Funky Friday, RoBeats) or for Patapon. No official Taiko no Tatsujin ms table.
- No source found on whether commercial games widen windows specifically for touch devices.

## 5. Calibration: audio vs visual vs input offset, tap tests, presentation, per-platform defaults

### Takeaway
A tap test can't isolate one latency type. Tapping to sound measures audio + input latency, and tapping to visuals measures video + input latency. The usual approach is therefore two offsets. One aligns visuals to audio (audio/visual offset). The other shifts judgement to match when players actually hit (input/judgement offset). Rhythm Doctor uses two phases, the second being a gameplay-like "7th-beat" tap test. Rhythm Quest uses a quick 4-sample visual tap test. Typical tap tests use about 10 taps and discard the min and max. No published per-platform default offsets were found.

### Cited Findings
- [Expert devlog, 2021] Three latencies: audio (buffering, mixing, Bluetooth, sound travel), visual (double-buffering, render queue, monitor refresh) and input (debouncing, frame-based input handling, wireless controllers). "we can never measure a single type of latency by itself using a tap test." Tapping to audio = audio + input. Tapping to visuals = video + input. The difference gives the audio/video offset. — [Rhythm Quest Devlog 10](https://rhythmquestgame.com/devlog/10.html)
- [Expert devlog] Rhythm Doctor splits calibration into two phases. The first aligns video and audio offset, and the second is a "seventh beat tap test" that measures input latency in a gameplay-like way. Samurai Shaver uses a test scene that simulates gameplay and gives immediate feedback. A typical tap test is about 10 taps with the min and max discarded. Rhythm Quest keeps only 4 samples and relies on the eye to spot inconsistency. Tap input during calibration must not play sounds, because their latency would disturb timing. The author recommends avoiding the "sit here and tap a button 10 times" approach in favour of something fast and visual. — [Rhythm Quest Devlog 10](https://rhythmquestgame.com/devlog/10.html)
- [Blog] Calibration is "the player's personal correction for their hardware, usually two offsets: one for visual sync and one for audio or input sync." — [Bugnet: bug tracking for rhythm games](https://bugnet.io/blog/bug-tracking-for-rhythm-games)
- [Blog] Latency and audio delay are distinct. A separate keyboard-latency offset is reportedly implemented by Rhythm Doctor, but its benefit is "inconclusive due to lack of data". — [eve-ning: Hit Sounds and Audio Offset impact on Syncing in Rhythm Games (Oct 2024)](https://eve-ning.github.io/2024/10/04/hitsounds.html)
- [Anecdotal guide] Rhythm Doctor players who still notice lag are advised to use an external audio-visual sync test and enter the numbers manually. — [ludo.guide: Rhythm Doctor advanced calibration](https://www.ludo.guide/guide/rhythm-doctor/tips-secrets/advanced-calibration-techniques)
- [Anecdotal] Patapon 1+2 Replay (2025) adds input-timing options. One review mentions a ten-point scale in the menu with no in-game guidance on how to set it. Seen only in search-result summaries; I could not open the page (HTTP 403). — [Push Square news (Apr 2025)](https://pushsquare.com/news/2025/04/bandai-namcos-ps5-patapon-remasters-will-fix-issues-sony-didnt-bother-to-on-ps4)

### Inferences
- [Inference] Laskar has a single offset (-200..+300 ms) applied to judgement. For a game where players hit to the music, this offset effectively equals audio output latency + input latency. It is the right first offset to have. A second "visual offset" only shifts the beat-indicator animation and can come later, if players report that visuals look off-beat while hits judge fine.
- [Inference] Auto-calibration for Laskar: play a metronome on the same audio path as the game music, ask for 12–16 taps on any drum, drop the first 4 (players are still locking in), take the median of the signed errors as the offset, and round to the 10 ms step. Show the scatter and let the player accept or retry. Use the median rather than the mean so a single stray tap doesn't skew the result. Keep tap feedback silent and visual only.
- [Inference] The +300 ms upper bound is sensible for Bluetooth headphones on Android, where audio latency can be hundreds of ms. The −200 ms lower bound is rarely needed, since negative offsets mean the player hits before the audio they hear. Consider an in-game hint when the measured offset exceeds about +150 ms ("Bluetooth audio detected?").
- [Inference] Per-platform defaults should come from Laskar's own telemetry. Log each player's final calibrated offset with `UserInputService.TouchEnabled`/platform, then set the default per platform to the median. No published per-platform defaults exist to copy.

### Gaps
- No published default offsets per platform (PC, iOS, Android, console) for Roblox or for comparable games.
- No Roblox-specific data on `Sound` playback latency (out of scope; covered by another researcher).
- Could not verify Rhythm Doctor's or Patapon Replay's calibration UI first-hand.

## 6. Networking: client-authoritative judgement vs server validation; anti-cheat; high ping and packet bursts

### Takeaway
Roblox RemoteEvents are reliable and ordered. Client→server sends are rate-limited to about 500 per second per client across all RemoteEvents, and excess sends are queued, not dropped. The docs say the server must be the source of truth and that client-side time (including `GetServerTimeNow`) can be tampered with. For PvE co-op, client-side judgement plus server plausibility checks (Laskar's current design) is the normal, proportionate approach. For leaderboards or PvP, the server should receive raw per-hit timestamps, recompute judgement itself, and check timestamps against packet arrival times. Even then, no server check can tell a well-built autoplayer from a perfect human, and Roblox rhythm games such as Funky Friday have long had autoplayer exploits.

### Cited Findings
- [Doc] "RemoteEvents are reliable and ordered". Lost messages are resent and arrive in firing order. `UnreliableRemoteEvent` guarantees neither delivery nor order, has no ordering relationship with RemoteEvents, and may drop payloads over 1,000 bytes. When a RemoteEvent is over the rate limit, its excess events are processed later, whereas an UnreliableRemoteEvent drops them. "To ensure fairness, the server has to be the source of truth for a game." — [Roblox Docs: Remote events and callbacks](https://create.roblox.com/docs/scripting/events/remote)
- [Doc] Client→server remote events are rate-limited to "approximately 500 requests per second, per client", shared across all remote events of the same type. RemoteEvents "buffer a large number of events before throwing" an error. — [creator-docs RemoteEvent.yaml](https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/reference/engine/classes/RemoteEvent.yaml)
- [Anecdotal, conflicting/old] Forum claims about remote limits range from "20 times per second" (attributed to old docs) to "600-700 per second-player with some burst capacity". These are superseded by the current doc figure above. One bug report says throttling kicks in at a lower threshold on some servers. — [DevForum: RemoteEvent limitations](https://devforum.roblox.com/t/2597139); [DevForum: Will firing server many times a second exceed the bandwidth limit](https://devforum.roblox.com/t/will-firing-server-many-times-a-second-exceed-the-bandwidth-limit/693011); [DevForum: Remote events sometime throttles…](https://devforum.roblox.com/t/remote-events-sometime-throttles-in-a-much-lower-threshold-in-some-servers-and-result-in-inconsistent-remote-event-firing-speed/1936046)
- [Doc] `Player:GetNetworkPing()` "Returns the round-trip, isolated network latency of the player in seconds… It doesn't involve data deserialization or processing." On the client it can only be called on the LocalPlayer. — [creator-docs Player.yaml](https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/reference/engine/classes/Player.yaml)
- [Doc] `GetServerTimeNow` is "not suitable for things like timed rewards" because client-side timing can be tampered with. — [creator-docs Workspace.yaml](https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/reference/engine/classes/Workspace.yaml)
- [Community practice] Server-side rate limiting per player and remote (a community module returns false when the limit is exceeded). Client-side throttling does not stop exploiters. Some developers kick or ban above a threshold (example: more than 60 fires per second). — [DevForum: Rate limiter module for Remotes](https://devforum.roblox.com/t/rate-limiter-module-for-remotes/616268); [DevForum: Insight on "Player seems to be spamming remote events"](https://devforum.roblox.com/t/insight-on-player-seems-to-be-spamming-remote-events/3410742)
- [Evidence of cheating in Roblox rhythm games] Funky Friday (Lyte Interactive) has had public autoplayer scripts. A GitHub mod project is "Originally a fork of wally-rblx's funky-friday-autoplayer". The author notes that Roblox's Hyperion anti-tamper (client-level) has made maintaining executors harder. — [GitHub: accountrev/funkychart](https://github.com/accountrev/funkychart). Community guides (low quality) say consistently perfect timing on every note is how such players get spotted and reported. — [example community article (low quality)](https://monitoring.toky.co/?p=10489)
- [Anecdotal] An exploiter flooding remotes mainly hurts their own session, not other players. — [DevForum: RemoteEvent limitations](https://devforum.roblox.com/t/2597139)

### Inferences
- [Inference] Laskar's PvE design is appropriate. A cheater can at most make their own squad act "perfect", which harms nobody in co-op. Cheap extra server checks:
  - (a) Beat index must be strictly greater than the last accepted command's end beat, which prevents replay and duplicates.
  - (b) Clamp quality to 0..1 and limit its effect, for example a damage multiplier of at most ×1.5.
  - (c) Accept at most 1 command per 4 beats per player, and treat more as spam.
  - (d) Check command ids against an allow-list.
  - (e) Silently ignore invalid packets instead of kicking. Honest players on lag spikes can trip edge cases.
- [Inference] Beat-window tolerance: the current −2..+1 beats (−1000..+500 ms) covers one-way latency up to about 1 s, which covers RTT ≈ 300–500 ms mobile connections plus a hitch. Because RemoteEvents are reliable and ordered, a lost packet causes head-of-line blocking, and several commands can then arrive together. Validate spacing using the claimed beat indices, not arrival times. You could also log `arrivalServerTime − claimedBeatTime − GetNetworkPing()/2` per player as a lag/abuse metric.
- [Inference] If leaderboards or PvP are added: send each hit's `os.clock()`-derived server-time stamp (4 per command, at most a few per second, far below the 500/s limit). Recompute the judgement on the server with the same window table. Reject hits stamped in the future (stamp > arrival time + small tolerance) or older than RTT + about 1 beat. Flag statistically implausible play for review rather than auto-ban, for example a standard deviation of hit error below about 5 ms over hundreds of hits, or zero misses across many songs. These checks block forged timestamps but cannot stop a bot that taps at plausible times. Roblox's Hyperion is the only defence against client-side automation.
- [Inference] Don't use `UnreliableRemoteEvent` for commands: a dropped command means a lost squad action. It is fine for cosmetic "drum hit" broadcasts to other players' screens.

### Gaps
- No published description of how specific Roblox rhythm games (Funky Friday, RoBeats) validate hits or scores server-side.
- No Roblox documentation on recommended plausibility checks for timing-based games.

## 7. Frame-rate drops: keeping judgement correct during lag spikes

### Takeaway
No Roblox source covers this directly. Because input is only timestamped when the engine processes it, a frame hitch delays every input that happened during it. Those inputs all get the post-hitch timestamp, so they judge late or miss through no fault of the player. The fixes are: compute beat time from an absolute clock rather than accumulated frame deltas, detect long frames, and give the benefit of the doubt for inputs that land right after a hitch.

### Cited Findings
- [Anecdotal, 2023] Sub-frame inputs are "aggregated onto the previous frame", and scripts must assume the input happened at either the previous or the next frame time. — [DevForum feature request](https://devforum.roblox.com/t/inputobjecttimesinceinputupdate-property-to-support-beyond-tick-rate-input-processing/2226487)
- [Anecdotal] Heavy Lua work (raycasting, physics, spawning instances) can stop input updates from keeping up, and players perceive random delay spikes. — [DevForum: Significant input delay (2019–2020, old)](https://devforum.roblox.com/t/significant-input-delay-camera-lag/344960); [DevForum: How to Reduce Input Lag?](https://devforum.roblox.com/t/how-to-reduce-input-lag/2985062)
- [Doc] The scheduler runs input, script events and rendering in sequence each frame, so a long script task delays the next frame's input processing. — [Roblox Docs: Task scheduler](https://create.roblox.com/docs/studio/microprofiler/task-scheduler)
- [Doc] `GetServerTimeNow()` and `os.clock()` are wall/elapsed clocks, not frame counters, so they stay correct across hitches. — [creator-docs Workspace.yaml](https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/reference/engine/classes/Workspace.yaml); [creator-docs os.yaml](https://raw.githubusercontent.com/Roblox/creator-docs/main/content/en-us/reference/engine/libraries/os.yaml)

### Inferences
- [Inference] Never derive beat position by summing `dt` from RunService events. Always compute `beatIndex = (now − startTime) / 0.5` from the absolute clock, so the beat grid never drifts after a hitch.
- [Inference] Hitch-aware judging: record `lastFrameClock = os.clock()` in a per-frame callback such as PreRender or Heartbeat. In the input handler, if `now − lastFrameClock > ~40 ms`, the real press time lies somewhere in `[lastFrameClock, now]`. Judge with the point in that interval closest to the target beat. This is favourable to the player and acceptable for PvE. For any ranked mode, log these "hitch-forgiven" hits.
- [Inference] Several drum presses inside one long hitch arrive in the same frame with near-identical timestamps. If a 4-hit command needs distinct beats, treat same-frame multi-presses after a hitch as "unknown order" and avoid punishing them, for example by cancelling the command instead of counting a mistimed miss.
- [Inference] Don't treat "no input on beat k" as a broken rhythm until the frame processing beat k + GOOD window has actually run. During a hitch, the miss check should wait for the next frame, which will deliver any queued inputs first.
- [Inference] Keep heavy work (squad spawning, VFX, pathfinding) out of the frames around beats, or spread it across frames with `task.defer` and budgets. This reduces hitches exactly when inputs are expected.
- [Inference] Server-side, apply the same tolerance: a client that just hitched sends its command late, which the −2 beat tolerance already absorbs.

### Gaps
- No Roblox-specific documentation or measurements on input behaviour during frame hitches (whether inputs are coalesced or dropped, and whether InputBegan order is preserved).
- No published Roblox rhythm-game postmortem on lag-spike handling.
